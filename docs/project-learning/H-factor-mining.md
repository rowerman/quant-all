# F1-F23 因子挖掘

自动因子挖掘不是“让模型随便写公式”。它是一条受控研究流程：把假设转换为候选表达式，经过技术检查、研究评估、统计诊断、人工审批和原子发布，最后才能进入正式因子目录。

核心代码位于 `research/mining`，Worker 位于 `research/mining_worker`，断网代码研究位于 `research/mining_sandbox`。

## F1：因子挖掘基础

### 先补基础知识

因子研究的起点通常是一个想法，例如“成交量突然增加可能意味着后续收益更高”。手工写一个公式只产生一个候选，自动挖掘的目标是系统地探索许多可检验表达式。

### 模块在项目中的位置

```mermaid
flowchart LR
  H[研究假设] --> C[候选因子]
  C --> G[技术与统计门禁]
  G --> R[人工审核]
  R --> P[正式发布]
  P --> E[评估/模型/回测]
```

### 它负责什么

它负责把研究想法变成可追踪、可评估、可审核的候选因子。

### 它不负责什么

它不自动批准候选，不训练交易模型，也不把候选的历史高分解释成稳定 Alpha。

### 输入与输出

输入是研究假设、冻结上下文和候选生成预算。输出是候选、证据、状态、审批记录和可发布产物。

### 一次典型流程

研究者提交假设，Worker 生成表达式，主服务校验并物化候选，再复用评估模块计算 RankIC、分位和相关性，最后等待人工决定。

### 结果如何理解

挖掘系统证明的是“候选经过了规定流程”，不是“候选一定能赚钱”。

### 常见误区与限制

- 候选不是正式因子。
- 通过技术门禁不等于经济有效。
- 搜索越多，偶然出现高分候选的机会越大。

### 本节范围

后续章节分别解释候选表达式、来源、评估和发布。

## F2：假设、机制与可证伪条件

### 先补基础知识

好的研究假设应说明三件事：为什么可能发生、用什么数据表示、什么结果会证明它不成立。可证伪条件能防止事后只挑有利证据。

### 模块在项目中的位置

假设进入 `MiningRunRequest`、`HypothesisCard` 或 V3 研究输入包。

### 它负责什么

它负责保存假设正文、经济机制、预期方向和失败条件。

### 它不负责什么

它不替统计评估证明机制真实存在，也不允许把自然语言直接当作可执行 SQL。

### 输入与输出

输出是稳定的研究输入、假设哈希和后续候选的来源引用。

### 一次典型流程

输入“过去 20 日成交量上升且价格未大涨，未来可能有反转”后，系统把机制、方向和可证伪条件冻结，Worker 只能在这些约束下提出候选。

### 结果如何理解

假设是研究问题的边界，不是候选公式本身。

### 常见误区与限制

- 解释得漂亮不等于可检验。
- 事后改写假设会破坏研究身份和证据链。
- 自由探索也需要记录方向和字段依赖。

### 本节范围

不展开自然语言解析模型。

## F3：DSL 与表达式

### 先补基础知识

DSL 是为特定任务设计的小型表达语言。项目用受控 DSL 表达因子公式，只允许冻结字段和冻结算子，不允许 Worker 任意执行 SQL 或 Python。

### 模块在项目中的位置

表达式结构和编译能力位于 `research/mining/expression.py`、`expression_compiler.py` 和目录契约。

### 它负责什么

它负责把候选表达式解析成结构化表达式，检查字段、算子、窗口、类型和深度，并编译为受控 DuckDB SQL。

### 它不负责什么

它不评估候选收益，也不允许任意路径、任意函数或任意数据库连接。

### 输入与输出

输入是表达式和冻结字段/算子目录。输出是规范化表达式、编译 SQL、依赖字段、回看窗口和语义哈希。

### 一次典型流程

Worker 返回一个表达式草稿，主服务重新解析它，确认所有名称都在冻结目录中，再生成 SQL 和候选身份。Worker 返回的名字不是权威值。

### 结果如何理解

DSL 把模型输出限制在可以审查和重复执行的范围内。

### 常见误区与限制

- 合法表达式不等于有预测能力。
- 表达式哈希和文字描述哈希不是一回事。
- 目录版本变化会使旧候选证据失效。

### 本节范围

不逐个解释 34 个冻结算子。

## F4：安全算子与表达式 DAG

### 先补基础知识

复杂因子通常由多个中间步骤组成。DAG 可以表示哪些计算节点被多个候选共享。安全约束则限制窗口、递归、深度和非法组合。

### 模块在项目中的位置

表达式规划、编译和批量物化位于 `expression_dag.py`、`candidate_batch.py` 和相关编译模块。

### 它负责什么

它负责检查表达式结构、避免循环依赖，并在多个候选共享计算时组织批量物化。

### 它不负责什么

它不判断共享节点的金融意义，也不让共享计算绕过候选级别的门禁。

### 输入与输出

输出是表达式计划、根节点、依赖图和候选级失败信息。

### 一次典型流程

四个候选都使用同一段滚动均值时，系统可以先生成共享宽表，再拆出每个候选的年度 Parquet；共享失败时按候选回退。

### 结果如何理解

DAG 主要解决可审查性和计算效率，不改变候选的经济含义。

### 常见误区与限制

- 共享节点错误可能影响多个候选，因此必须有候选级校验。
- 批量路径和串行路径要保持字节或结果一致。
- 复杂度上限是安全门，不是质量评分。

### 本节范围

不展开 DAG 节点调度算法。

## F5：候选身份与来源追踪

### 先补基础知识

研究中同一个候选可能被多次提出。如果没有稳定身份，就无法判断是重复实验还是新候选，也无法把最终发布追溯回原始来源。

### 模块在项目中的位置

候选定义、内容哈希、语义哈希和 provenance 位于 `candidate.py`、`contract_types.py`、V2/V3 source 模块。

### 它负责什么

它负责生成稳定候选 ID，记录表达式、方向、依赖、发现位置和来源引用。

### 它不负责什么

它不评价候选是否优秀，也不把来源文本作为因子值。

### 输入与输出

输出包括候选内容哈希、语义哈希、上下文哈希、来源类型和候选状态。

### 一次典型流程

相同表达式重新提交时，内容哈希识别重复；自由探索即使改写措辞，只要冻结机制和字段组合相同，也可被语义哈希识别为同一方向。

### 结果如何理解

候选身份是审计和防重复搜索的基础。

### 常见误区与限制

- 文字不同不一定是新候选。
- 上下文变化会使旧证据不能直接复用。
- 候选 ID 不等于正式因子名。

### 本节范围

不列出所有哈希字段排除规则。

## F6：统一输入契约

### 先补基础知识

项目当前有手工假设、自由探索、资料驱动和 CoSTEER 等来源。它们的材料形式不同，但最终都要进入统一的输入、候选和证据流程。

### 模块在项目中的位置

V3 输入和来源适配位于 `v3_sources.py`、`v3_contracts.py` 和 V3 存储。

### 它负责什么

它负责把不同来源转换成统一的研究输入包和来源引用。

### 它不负责什么

它不自动提升来源可信度，也不把资料来源直接当作审批结论。

### 输入与输出

输入是来源特定材料，输出是 `ResearchInputEnvelope`、`ResearchSourceReference`、候选绑定和来源哈希。

### 一次典型流程

手工假设提供正文，自由探索提供种子和方向池，资料驱动提供研究字段，CoSTEER 提供人工提升产物；四者都先绑定来源，再进入候选生成。

### 结果如何理解

统一契约让不同入口共享相同的质量和审批边界。

### 常见误区与限制

- 四类来源不是四种质量等级。
- 来源引用和候选内容要分开保存。
- 来源材料变化可能使运行需要重新审核。

### 本节范围

各来源的细节在 F9 和 F21 继续说明。

## F7：Worker 与模型调用基础

### 先补基础知识

Worker 是独立进程，用来调用外部模型生成研究材料或候选。主服务把它当成不可信的外部协作者，而不是数据库内的业务逻辑。

### 模块在项目中的位置

Worker 客户端在 `research/mining/worker_client.py` 和 `search_worker_client.py`，服务在 `research/mining_worker/service.py`。

### 它负责什么

它负责提交任务、接收响应、报告健康状态、处理超时、取消和错误。

### 它不负责什么

它不直接读取行情库、候选库或正式因子目录，也不决定候选最终身份。

### 输入与输出

输入是冻结上下文、提示约束和任务请求。输出是协议化响应、表达式草稿、研究字段或搜索决策。

### 一次典型流程

主服务提交请求，Worker 在隔离环境中调用模型，返回受限 JSON；主服务重新校验所有内容后才进入下一阶段。

### 结果如何理解

Worker 只提供研究候选或材料，不提供可信结论。

### 常见误区与限制

- Worker 返回成功不代表候选通过质量门禁。
- 网络超时和模型输出格式错误是正常失败路径。
- 完整 prompt 和响应不能随意写入日志。

### 本节范围

不展开外部模型供应商 API。

## F8：Worker 协议与版本

### 先补基础知识

协议规定任务和响应的字段、枚举、哈希和大小限制。版本化是为了让旧运行仍可解释，同时允许新流程增加能力。

### 模块在项目中的位置

协议位于 `research/mining_worker/protocol*.py` 和主项目的 worker client 模块。

### 它负责什么

它负责定义 V1、V2、V3 以及研究转换、代码提案等任务的通信契约。

### 它不负责什么

它不替主服务做候选校验，也不决定发布资格。

### 输入与输出

输出是可验证、可哈希、大小受限的 JSON 对象和错误分类。

### 一次典型流程

主服务按协议构造请求，Worker 返回响应，客户端先解析版本和字段，再将内容交给领域校验器。未知字段或非法枚举会拒绝。

### 结果如何理解

协议版本说明“如何沟通”，不说明“候选质量”。

### 常见误区与限制

- 兼容旧协议不等于共享所有新功能。
- 改协议字段可能影响请求哈希和运行恢复。
- Worker 与主项目使用独立依赖环境。

### 本节范围

不列出每个协议类的完整 JSON。

## F9：资料驱动研究材料

### 先补基础知识

研究报告可能包含因子名称、机制、公式、变量、方向和可证伪条件。资料驱动入口的任务是把文本中的研究线索整理成结构化草稿，而不是直接相信报告结论。

### 模块在项目中的位置

解析位于 `research_factor_extraction*`、`research_factor_conversion*` 和资料文档流程。

### 它负责什么

它负责发现文本材料、分类金融研报、抽取字段、记录证据状态，并把合格草稿转换成受控候选输入。

### 它不负责什么

它不把论文或报告的历史回测结果当成当前项目的验证结果。

### 输入与输出

输入是文本型 PDF 或研究材料。输出是字段草稿、来源定位、explicit/inferred/missing 状态、转换结果和失败分类。

### 一次典型流程

系统读取文档，提取公式和机制，标记哪些字段是原文明确写出、哪些是推断、哪些缺失，再交给受控 DSL 转换和项目自己的评估。

### 结果如何理解

资料提供候选来源和研究方向，不提供本地数据上的有效性证明。

### 常见误区与限制

- 文本抽取可能漏掉公式或单位。
- 研究报告使用的股票池和时间区间可能与项目不同。
- 缺少关键字段时应拒绝转换，而不是猜测。

### 本节范围

不展开 PDF 文本解析技术。

## F10：代码沙箱与安全边界

### 先补基础知识

有些研究想法需要编写临时代码或在 Qlib 快照上实验。让外部模型代码直接接触主机和正式数据风险很高，因此需要隔离沙箱。

### 模块在项目中的位置

沙箱位于 `research/mining_sandbox`，容器配置在该目录的 Dockerfile 和锁文件。

### 它负责什么

它负责限制路径、模块、运行时间和产物类型，并把代码、指标和知识证据封存为人工审核材料。

### 它不负责什么

它不把沙箱结果自动发布为正式因子，也不让沙箱绕过正式 DSL。

### 输入与输出

输入是代码提案、冻结数据快照和任务契约。输出是受限研究指标、artifact 清单、代码哈希和反馈。

### 一次典型流程

提案先经过 AST 和路径策略检查，再在隔离环境执行，读取允许的快照，最后把结果写入受控产物目录。

### 结果如何理解

沙箱降低了执行风险，但不提高候选的金融可信度。

### 常见误区与限制

- 沙箱隔离不等于代码逻辑正确。
- 产物清单和哈希缺失时不能人工提升。
- M5 默认关闭，输出只能作为审核材料。

### 本节范围

不讲容器内核安全和系统调用细节。

## F11：研究工具与知识输入

### 先补基础知识

研究者需要查看字段目录、已有因子、评估摘要和统计工具。工具的作用是提供受控信息，避免 Worker 自己连接数据库或读取任意路径。

### 模块在项目中的位置

工具网关、知识合同和搜索支持位于 `research/mining` 与 `mining_sandbox`。

### 它负责什么

它负责把允许的字段、因子、统计和历史证据以有限、可审计的形式提供给研究流程。

### 它不负责什么

它不允许 Worker 执行任意 SQL，也不替研究者自动决定方向。

### 输入与输出

输出是工具结果、知识 artifact、输入哈希和使用记录。

### 一次典型流程

Worker 请求某个字段说明或已有因子摘要，主服务在开发期执行工具并返回有限结果，调用次数和内容进入运行证据。

### 结果如何理解

工具输出是研究上下文，不是新的数据资产。

### 常见误区与限制

- 工具只能看到冻结允许的窗口。
- 工具调用次数受预算限制。
- 知识输入变化会影响候选和运行哈希。

### 本节范围

不列出每个工具的 JSON 契约。

## F12：候选评估

### 先补基础知识

候选必须经过“能不能算”“算出来是否合理”“是否有预测关系”“是否重复已有因子”等多个检查。

### 模块在项目中的位置

评估位于 `research/mining/evaluation*`，并复用 `calculate` 的面板和指标。

### 它负责什么

它负责物化候选因子、运行技术门禁、轻量 RankIC、完整评估和候选相关性。

### 它不负责什么

它不自动决定人工审批，也不把候选写进正式内置因子族。

### 输入与输出

输入是候选定义和冻结上下文。输出是候选 Parquet、评估报告、门禁状态、输入哈希和失败诊断。

### 一次典型流程

候选先在独立运行目录物化，再检查行集、覆盖率、前视和数值；通过后复用评估面板计算 IC、分位、衰减、风格和相关性。

### 结果如何理解

候选评估与正式因子评估使用相同口径，便于比较，但候选仍处于研究阶段。

### 常见误区与限制

- 轻量筛选通过不代表完整评估通过。
- 候选相关性通常只对正式 peer 计算。
- 评估证据依赖冻结数据和规则版本。

### 本节范围

不重复 D1-D6 的指标解释。

## F13：技术、开发与选择阶段

### 先补基础知识

不同阶段回答不同问题：技术阶段看能否正确计算，开发阶段看研究信号，选择阶段比较候选和稳定性，不能把它们混成一次分数。

### 模块在项目中的位置

阶段执行由 `search_orchestrator`、`search_evaluation` 和 V3 runtime 管理。

### 它负责什么

它负责按固定顺序推进候选，并把每阶段证据写入运行轨迹。

### 它不负责什么

它不允许后续测试段结果反向提示 Worker 或重排候选。

### 输入与输出

输出是 technical、development、selection、full 和 test holdout 阶段报告及状态。

### 一次典型流程

候选先完成技术检查，再在开发期做快速筛选；选择期使用确定性控制器比较稳定性和相关性；通过后才进入完整评估和一次性测试段。

### 结果如何理解

阶段分离是为了减少把同一份结果反复用于搜索和验证。

### 常见误区与限制

- 选择期结果仍可能被搜索过程间接影响。
- 完整评估不等于最终留出。
- 每阶段必须保留输入哈希和可见窗口。

### 本节范围

下一节专门说明完整评估和测试留出。

## F14：完整评估与测试留出

### 先补基础知识

测试留出是一次性验证，不能在看到结果后继续调参。自动挖掘中的模块测试段也遵守这一原则。

### 模块在项目中的位置

完整评估和测试执行器位于 `search_orchestrator`、`search_v3` 和相关 recovery 模块。

### 它负责什么

它负责在候选冻结后，分别执行完整研究窗口和一次性测试段，并封存结果。

### 它不负责什么

它不向 Worker 返回测试段结果，也不根据测试结果替换候选。

### 输入与输出

输出是封存报告、测试领取批次、候选状态和运行收口状态。

### 一次典型流程

开发与选择完成后冻结候选顺序和 ID，领取测试段，逐候选执行一次，记录结果；进程中断后按已有证据恢复，不重复完成项。

### 结果如何理解

测试段结果是对冻结候选的验证，不是继续搜索的反馈。

### 常见误区与限制

- 反复读取测试结果再改公式会消耗测试独立性。
- 测试段与模型最终留出可能存在区间关系，需按项目限制解读。
- 恢复机制只能恢复证据，不能恢复外部模型的未知状态。

### 本节范围

不展开恢复事件的全部字段。

## F15：统计诊断与多重检验

### 先补基础知识

搜索很多候选时，即使所有候选都没有真实能力，也可能有少数因为随机波动看起来很好。这叫多重比较或搜索选择问题。

### 模块在项目中的位置

统计诊断位于 `search_statistical_diagnostics.py`、`search_research_quality.py` 和选择诊断模块。

### 它负责什么

它负责提供 Newey-West、稳定性、年度同号率、多重检验和搜索质量诊断。

### 它不负责什么

它不把单个 p 值当成最终交易证明，也不替预注册门槛做人工判断。

### 输入与输出

输出是诊断报告、警告、有效样本、相关簇和选择证据。

### 一次典型流程

候选在开发期得到 RankIC 序列后，系统检查时序相关、年度稳定性和多重候选下的偶然性，再把结果交给确定性选择器。

### 结果如何理解

统计诊断是在降低“看起来好但只是偶然”的风险，不是制造真实信号。

### 常见误区与限制

- p 值不能解决数据挖掘带来的选择偏差。
- 重叠标签会影响标准误和 t 值解释。
- 诊断需要与经济门槛、成本和稳定性结合。

### 本节范围

不推导 Newey-West 公式。

## F16：稳定性与交易成本证据

### 先补基础知识

一个候选如果只在某一年、某个股票池或忽略成本时有效，实际价值可能很低。稳定性和成本分析检查信号是否跨环境保留。

### 模块在项目中的位置

稳定性、成本和组合诊断由 mining search、evaluation 和 downstream 组件共同完成。

### 它负责什么

它负责检查候选在时间、股票池、持有期和成本假设变化下的表现。

### 它不负责什么

它不模拟所有盘口细节，也不保证稳定候选未来仍有效。

### 输入与输出

输出包括年度结果、换手、分位收益、成本敏感性、风格和相关性证据。

### 一次典型流程

选择器先看开发期多个窗口，再把候选交给完整账本或成本代理，观察高分是否依赖过高换手或特定市场阶段。

### 结果如何理解

稳定性降低研究脆弱性，但不会消除未来不确定性。

### 常见误区与限制

- 成本模型只是近似。
- 稳定性检查仍在历史样本内。
- 低换手不代表信号强，高收益也不一定来自候选本身。

### 本节范围

不重复回测成本模型的执行细节。

## F17：搜索控制与试验记录

### 先补基础知识

搜索预算决定可以尝试多少轮、多少候选、多少模型调用。预算越大，探索能力越强，但选择偏差和资源消耗也增加。

### 模块在项目中的位置

预算和试验记录位于 `search_contracts.py`、`search_trials.py`、`search_scorecard.py` 和 orchestrator。

### 它负责什么

它负责限制 turn、分支、候选、工具调用、完整评估和 LLM 调用，并记录每次尝试的结果。

### 它不负责什么

它不保证预算内找到好因子，也不允许越过冻结上限。

### 输入与输出

输出是 trial record、scorecard、预算状态、停止原因和搜索决策。

### 一次典型流程

每轮生成候选并记录接受、拒绝、重复、非法和门禁结果；连续若干轮无改善时按规则停止，不让模型无限探索。

### 结果如何理解

试验记录让研究者知道“搜索做过什么”，而不只是看到最终候选。

### 常见误区与限制

- 预算停止不等于研究结论成立。
- 试验越多，最终候选的选择偏差越大。
- 修改预算会改变运行身份和可比性。

### 本节范围

不列出全部默认预算数值。

## F18：状态机与运行恢复

### 先补基础知识

长时间研究任务可能被进程中断、Worker 超时或服务重启。状态机记录运行和候选目前处于哪个阶段，恢复逻辑决定从哪里继续。

### 模块在项目中的位置

状态定义位于 `states.py`、`search_states.py` 和 V3 states；恢复位于 runtime、recovery 和 storage。

### 它负责什么

它负责推进运行、候选、证据、审核和发布状态，并在中断后根据持久化证据恢复。

### 它不负责什么

它不凭空补造缺失证据，也不把运行中的候选直接标成成功。

### 输入与输出

输出是状态事件、当前投影、恢复计划和终态收口。

### 一次典型流程

候选领取后进程中断，恢复器读取领取事件和已有评估证据，冻结候选顺序，只重跑未完成项，最后更新运行和候选状态。

### 结果如何理解

恢复能力保证“任务不丢、已完成工作不重复”，不是保证 Worker 结果可重复。

### 常见误区与限制

- 状态投影必须与事件证据一致。
- 运行失败和候选失败是不同层次。
- 取消、超时和崩溃应有不同状态语义。

### 本节范围

不逐事件解释状态迁移表。

## F19：存储、事件与证据链

### 先补基础知识

数据库表保存当前可查询状态，事件和证据保存“发生过什么”。二者结合，才能既方便页面读取，又能追溯运行历史。

### 模块在项目中的位置

存储位于 `storage*.py`、`storage_v2*.py`、`storage_v3*.py` 和 `factor_mining.duckdb`。

### 它负责什么

它负责保存运行、候选、尝试、评估、审批、发布、哈希和恢复事件。

### 它不负责什么

它不把日志当作唯一状态，也不允许读取一个未完成或哈希不一致的证据包当作正式结论。

### 输入与输出

输出是可查询的状态投影、追加证据、链式轨迹和运行目录 artifact。

### 一次典型流程

候选评估报告先写临时文件，校验和哈希通过后原子替换；数据库事务保存证据引用和状态事件，页面读取投影。

### 结果如何理解

证据链是候选从生成到发布的 provenance。

### 常见误区与限制

- 日志解释执行过程，数据库和 artifact 决定业务事实。
- 任何输入规则变化都可能使旧证据失效。
- 只保存最终分数会丢失失败尝试和选择过程。

### 本节范围

不解释 DuckDB schema 的全部表字段。

## F20：审核、审批与原子发布

### 先补基础知识

审核是人确认研究材料和证据是否足够；发布是把已批准候选写入正式因子目录。批准和发布不是同一个动作。

### 模块在项目中的位置

审核和发布位于 `review.py`、`publication.py`、`storage_publications.py` 和页面服务。

### 它负责什么

它负责检查候选资格、记录人工决定、构建正式 `mined` 族并原子切换可见版本。

### 它不负责什么

它不替人工判断经济机制，也不在半成品目录上直接覆盖正式因子。

### 输入与输出

输入是批准候选、证据哈希、上下文哈希和发布批次。输出是正式定义、版本目录、符号链接和提交状态。

### 一次典型流程

发布服务先重建全历史因子并校验行集、覆盖率和前视，再写入版本目录，最后原子替换 `data/factors/mined` 链接。失败时恢复旧版本。

### 结果如何理解

原子发布保证下游看到的是旧版本或完整新版本，不会看到半个候选族。

### 常见误区与限制

- 人工批准不等于实盘批准。
- 发布资格要求运行和候选状态仍然有效。
- 正式构建内置族不会自动覆盖 mined。

### 本节范围

不讲符号链接和事务的系统调用细节。

## F21：V1/V2/V3 兼容与迁移

### 先补基础知识

协议升级时，旧运行不能立即消失。兼容层让旧结果继续可读，迁移则把旧数据按明确规则转换到新结构。

### 模块在项目中的位置

兼容和迁移位于 `storage_v2`、`storage_v3`、`v3_migration_*` 和启动预检。

### 它负责什么

它负责区分 V1、V2、V3 的输入、状态、证据和发布来源，并提供显式迁移入口。

### 它不负责什么

它不自动把旧库隐式改写成新库，也不允许旧状态绕过新审批门禁。

### 输入与输出

输出是迁移状态、版本来源、兼容读取结果和迁移后的新证据。

### 一次典型流程

启动时发现 V1/V2 库，先报告迁移状态；用户显式执行迁移后，系统建立 V3 schema 和来源绑定，旧运行仍保留历史身份。

### 结果如何理解

版本桥接保护的是可追溯性，不是让不同协议的结论自动可比。

### 常见误区与限制

- V1/V2/V3 的证据阶段不完全相同。
- 迁移失败不能靠删除旧库解决。
- 页面状态应使用当前 contract 的投影，而不是按批次名称猜测。

### 本节范围

不展开迁移 SQL 和回滚脚本。

## F22：编排、Worker 故障与恢复

### 先补基础知识

编排器负责安排多个阶段和多个候选。Worker 可能超时、不可用、返回非法内容或被取消，主服务必须把这些情况转成可恢复状态。

### 模块在项目中的位置

编排位于 `search_orchestrator*.py`、`orchestrator.py`、worker client 和 recovery 模块。

### 它负责什么

它负责提交任务、推进阶段、执行预算、处理失败、取消、重试和恢复。

### 它不负责什么

它不吞掉所有异常，也不把 Worker 失败伪装成候选失败之外的成功。

### 输入与输出

输出是后台事件、阶段状态、错误码、重试次数和最终运行状态。

### 一次典型流程

Worker 超时后，编排器记录失败并根据协议决定是否重试；若已有候选证据，则恢复时不重复执行完成项；连续失败时运行收口为失败或不可恢复。

### 结果如何理解

故障处理是研究可追溯性的组成部分，不能只看最终候选数量。

### 常见误区与限制

- 重试可能增加外部模型调用和成本。
- 取消通常在阶段边界生效。
- Worker 可用不代表返回内容合规。

### 本节范围

不展开 HTTP 超时和 Docker 网络配置。

## F23：挖掘页面与联合场景

### 先补基础知识

页面把复杂研究流程变成启动、查看、审核和发布几个动作，但页面只是入口，真正的状态和证据仍由挖掘服务和存储决定。

### 模块在项目中的位置

页面服务位于 `apps/monitor/backend/mining*`，前端位于 `apps/monitor/frontend/mining*`。

### 它负责什么

它负责展示运行、候选、证据、审核和发布状态，并提供受控操作入口。

### 它不负责什么

它不重新计算候选、不绕过审批，也不直接写正式因子目录。

### 输入与输出

输入是 API 请求和用户审核动作。输出是 SSE/JSON 状态、候选详情、批次状态和错误提示。

### 一次典型流程

用户启动 V3 自由探索，页面显示运行状态；候选完成后查看证据并审批；发布批次后台构建和校验，完成后页面看到正式 `mined` 版本。

### 结果如何理解

页面显示的是运行状态投影，不是金融结论本身。

### 常见误区与限制

- 页面显示 approved 不代表发布成功。
- 发布失败可能已经保留审核证据，但正式目录仍是旧版本。
- 需要用 run_id、candidate_id 和 batch_id 定位日志和数据库。

### 本节范围

具体页面布局和 JavaScript 事件留到监测应用文档。
