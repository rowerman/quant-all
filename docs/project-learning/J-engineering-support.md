# P1-P5 工程支撑

工程支撑让数据、因子、模型、回测、挖掘和 Web 模块可以被重复运行、定位和验收。它不直接产生金融信号，但决定研究结果能否被复现和追责。

## P1：路径、配置与依赖

### 先补基础知识

项目运行时会使用数据目录、数据库、日志目录、配置文件和环境变量。如果不同模块各自拼路径或各自解释配置，很容易出现“读取了另一份数据”的问题。

### 模块在项目中的位置

路径集中在 `core/common/paths.py`，项目依赖在 `pyproject.toml`、`requirements.txt` 和锁文件，配置在 `configs`。

### 它负责什么

它负责统一项目根目录、数据根目录、数据库、因子、模型、挖掘、日志和文档路径，并定义依赖和配置入口。

### 它不负责什么

它不验证数据金融含义，也不自动替外部服务补齐权限或密钥。

### 输入与输出

输入是项目结构、环境变量和配置文件。输出是各业务模块共享的路径常量、包映射和默认配置。

### 一次典型流程

设置 `QUANT_DATA_DIR` 后，主库、因子、模型和结果目录统一切换到指定数据根目录；代码仍通过 `common.paths` 读取，不需要到处修改相对路径。

### 结果如何理解

路径一致性是数据复现的基础。换了数据目录，可能就换了整套研究资产。

### 常见误区与限制

- `.env` 不是所有启动脚本都会自动加载。
- 主项目和 Worker 使用不同 Python 环境和锁文件。
- 相对路径通常以项目根为基准，不以当前 shell 目录为基准。

### 本节范围

不解释打包后安装路径的全部兼容分支。

## P2：日志与错误

### 先补基础知识

日志记录“运行时发生了什么”，错误码记录“在哪个业务域、哪类契约失败”。二者结合才能从页面请求追到具体模块。

### 模块在项目中的位置

共享日志在 `core/common/logging_conf.py`，各业务有自己的 logging wrapper；错误树分布在 `calculate.errors`、`alpha.errors`、`backtest.errors`、`mining.errors` 和 `backend.errors`。

### 它负责什么

它负责按模块分目录记录日志、轮转大文件、定义稳定错误码并把错误映射到 Web 响应。

### 它不负责什么

它不把异常吞掉，也不把日志当成数据库状态的替代品。

### 输入与输出

输出是按业务域组织的日志文件、错误码、请求编号和可定位的错误响应。

### 一次典型流程

用户拿到 `request_id` 和错误码后，先按错误码找到业务域，再进入对应日志目录，最后对照数据库运行状态、manifest 或输入快照确认事实。

### 结果如何理解

日志是执行过程证据，错误码是定位索引，业务状态仍以对应数据表和 artifact 为准。

### 常见误区与限制

- 日志写入故障不能变成业务成功。
- Worker 日志不能写入 Key、Bearer Token、完整 prompt 和完整响应。
- 多进程同时写同一日志目录可能造成轮转冲突。

### 本节范围

不逐一列出所有业务错误码。

## P3：测试层级

### 先补基础知识

单元测试检查一个函数或小模块；联合测试检查多个模块连接；集成、真实数据、原生、Docker 和浏览器测试检查更大的运行边界。

### 模块在项目中的位置

测试位于根 `tests`、评估测试、回测测试和监测 backend tests，pytest 配置在 `pyproject.toml`。

### 它负责什么

它负责验证数据契约、数值语义、状态迁移、跨模块联动和运行资源边界。

### 它不负责什么

它不把测试通过解释为金融收益有效，也不自动覆盖外部供应商的行为。

### 输入与输出

输出是通过/失败、测试层级、marker、日志和必要的性能证据。

### 一次典型流程

默认快速测试排除真实数据、原生、Docker、浏览器和付费调用；需要完整验收时再按 marker 运行对应层级，避免把慢测试误当成日常检查。

### 结果如何理解

测试证明的是某些可观察行为在给定环境下成立，不是整个研究系统被数学证明正确。

### 常见误区与限制

- 单元测试全绿仍可能有联动错误。
- 真实数据测试与合成夹具测试回答不同问题。
- 失败后应优先运行与修改范围相关的测试，而不是盲目全量重跑。

### 本节范围

不列出全部测试文件和 marker。

## P4：运行工具与证据

### 先补基础知识

研究工程需要知道“这次运行用的是什么输入、花了多少资源、输出是否能复现”。demo、审计、benchmark 和浏览器工具分别服务不同问题。

### 模块在项目中的位置

工具位于 `tools`、`examples`、`AiRecord/evidence` 和各业务文档。

### 它负责什么

它负责提供合成演示、数据审计、性能基准、浏览器验收、运行证据和修改追踪。

### 它不负责什么

它不替正式业务模块保存核心状态，也不把性能基准转成收益结论。

### 输入与输出

输出包括 demo 数据、报告、截图、基准 JSON、日志和 AiRecord 记录。

### 一次典型流程

修改原生核后，先用固定合成数据做契约测试，再用固定真实数据基准比较耗时和哈希，最后把证据写入对应版本目录。

### 结果如何理解

工具证据把“我认为改对了”变成可以复查的记录。

### 常见误区与限制

- benchmark 只适用于固定机器、数据和版本组合。
- demo 使用合成数据，不代表真实市场表现。
- 浏览器截图证明页面流程，不证明底层研究结论。

### 本节范围

不展开每个工具的 CLI 参数。

## P5：已知限制与维护边界

### 先补基础知识

一个系统的限制可以来自数据、统计、交易、外部服务、资源或环境。把限制分类，比笼统地说“可能有误差”更有用。

### 模块在项目中的位置

限制记录分布在 `README.md`、`docs/limitations.md`、各业务专题文档和 `AiRecord`。

### 它负责什么

它负责把已知缺口、不可验证边界、研究假设和维护规则公开记录下来。

### 它不负责什么

它不自动消除限制，也不把“已记录”解释成“已解决”。

### 输入与输出

输出是数据口径、研究有效性、交易仿真、外部服务、资源和维护方面的限制清单。

### 一次典型流程

发现某个回测结果没有基准数据时，系统应让组合指标继续返回、跳过基准指标，并在文档和测试中记录边界，而不是填入虚假的基准收益。

### 结果如何理解

限制是研究结论的一部分。没有边界说明，数字就无法被正确解释。

### 常见误区与限制

- 项目不是实盘系统，没有券商接入、实时行情和盘口撮合。
- 最终留出窗口已消耗，不能用同一窗口重新调参宣称独立成功。
- 外部 Tushare、模型供应商和 Docker 镜像不可用时，工程链路会受影响。

### 本节范围

具体业务限制应回到对应模块文档，而不是只看本节摘要。
