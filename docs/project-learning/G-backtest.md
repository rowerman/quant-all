# T1-T22 回测层

回测层回答的问题不是“历史收益率是多少”，而是：

> 如果在历史上按照指定信号、资金、价格、交易限制、费用和公司行动执行，组合状态会怎样变化？

回测必须区分目标和实际：目标权重是策略想要的组合，成交和账本才是实际组合。

核心代码位于 `trading/backtest`，结果库默认是 `data/databases/backtest.duckdb`。

## T1：回测与组合基础

### 先补基础知识

一个组合由现金和多只股票组成。策略每天可能产生信号，信号经过选股和权重分配形成目标组合，再由订单和成交改变真实持仓。

```text
信号 -> 目标权重 -> 订单 -> 成交 -> 持仓/现金 -> 净值
```

### 模块在项目中的位置

```mermaid
flowchart LR
  S[策略信号] --> W[目标权重]
  W --> O[订单]
  O --> F[成交与费用]
  F --> L[账本]
  L --> R[日结果与指标]
```

### 它负责什么

它负责在历史行情上模拟组合从一天到下一天的状态变化。

### 它不负责什么

它不训练模型、不发现因子，也不把研究指标直接当成成交结果。

### 输入与输出

输入是策略规格、市场面板、初始现金和运行区间。输出是日结果、持仓、订单、拒单、成本、公司行动和指标。

### 一次典型流程

周五收盘产生目标，下一交易日开盘尝试交易，系统更新现金和持仓，收盘按可用价格估值，形成当天净值。

### 结果如何理解

回测结果是“在明确规则下的历史模拟”，不是未来收益承诺。

### 常见误区与限制

- 目标组合不等于实际组合。
- 理论收益不等于扣成本后的净值。
- 回测越接近真实交易，越依赖数据质量和规则假设。

### 本节范围

后续各节拆开解释每个执行边界。

## T2：策略规格与运行身份

### 先补基础知识

策略不是一句“买高分股票”。它还包括股票池、信号时间、调仓频率、权重方式、成本、基准和风险限制。版本化是为了保证旧运行不会因为配置变化而悄悄改变。

### 模块在项目中的位置

策略结构位于 `trading/backtest/specs.py`，策略和运行记录由 `BacktestStore` 管理。

### 它负责什么

它负责定义不可变的策略版本，并把每次运行绑定到具体配置和哈希。

### 它不负责什么

它不执行订单，也不允许运行时覆盖直接修改历史策略版本。

### 输入与输出

`StrategySpec` 包含 signal、portfolio、rebalance、execution、costs、benchmark 和 risk 等部分；运行还会保存 `config_hash` 和输入快照。

### 一次典型流程

用户创建策略第一版，随后运行可以临时覆盖日期、股票池或基准，但这些覆盖进入本次运行快照，不改变已存在的策略版本。

### 结果如何理解

运行 ID 加策略版本是回测结果的身份。没有身份绑定，就无法判断两个净值曲线是否来自同一规则。

### 常见误区与限制

- 修改 JSON 默认值可能改变新运行，但不应改变旧运行解释。
- 运行级覆盖不是新策略版本，但会改变本次结果。
- 策略版本相同而源码 provider 变化，会触发快照冲突。

### 本节范围

不展开策略 schema 的全部字段校验。

## T3：回测输入数据契约

### 先补基础知识

回测成交使用原始价，因为真实交易发生在当时的市场价格上。后复权价适合研究因子和标签，但不能直接拿来模拟现金和股数。

### 模块在项目中的位置

输入面板由 `backtest.data.MarketData` 表示，读取和快照位于 `data.py`、`snapshot.py` 和 `provider_schema.py`。

### 它负责什么

它负责提供形状一致的开收盘价、状态、因子、股票池、公司行动和基准数据。

### 它不负责什么

它不替调用方修复面板错位，也不在缺数据时假设股票可以成交。

### 输入与输出

典型字段包括 `open`、`close`、`can_buy_close`、`can_sell_close`、`amount_cny`、因子矩阵、行业和基准收益。

### 一次典型流程

系统读取交易日和股票列后，检查所有矩阵是否同形、日期是否对齐、因子是否存在、股票池和行业是否一致，再生成输入快照。

### 结果如何理解

输入契约决定回测看到的市场世界。错位一行就可能把 A 股票的价格配给 B 股票。

### 常见误区与限制

- 研究价和执行价必须分工。
- 输入快照是复现入口，不是额外的收益调整。
- 面板超过硬上限时必须分块或拒绝。

### 本节范围

不逐列列出 `MarketData` 的全部字段。

## T4：信号时点与执行时点

### 先补基础知识

如果使用当天收盘后才知道的信息，就不能假设当天收盘前已经成交。项目默认是收盘生成信号，下一可交易日执行。

### 模块在项目中的位置

时序由 `RebalanceSpec`、`signals.py` 和执行引擎共同约束。

### 它负责什么

它负责把信号日期和真正可以下单的执行日期分开。

### 它不负责什么

它不预测开盘价，也不把收盘信号直接当成收盘成交事实。

### 输入与输出

输入是调仓频率、`signal_at` 和 `execute_at`。输出是信号日目标矩阵和执行日订单。

### 一次典型流程

周五收盘计算因子排序，若下一交易日是周一，则周一开盘按目标权重下单；如果周一停牌或涨停，实际成交会被拒绝或延期。

### 结果如何理解

信号时间决定信息是否可用，执行时间决定价格和交易约束。两者混在一起会造成前视偏差。

### 常见误区与限制

- “当天收盘买入”只有在数据和策略明确允许时才成立。
- 研究标签的买入通道不一定等于回测的真实执行。
- 延迟执行会改变持仓和后续目标。

### 本节范围

不展开所有调仓频率的日历规则。

## T5：股票池与可交易性

### 先补基础知识

股票池决定“允许考虑哪些股票”，可交易性决定“今天能不能买或卖”。一只股票可能属于指数，但因为停牌或涨停暂时不能成交。

### 模块在项目中的位置

股票池解析位于 `backtest.universe`，市场状态来自数据层，执行校验位于 `risk.py`、`orders.py` 和账本。

### 它负责什么

它负责在每个交易日生成股票池成员和 eligible 条件，并阻止不合规则的目标权重。

### 它不负责什么

它不预测成交概率，也不自动把不能交易的股票替换成另一只股票。

### 输入与输出

输入是 `all_a` 或指数池、上市天数、ST、停牌、涨跌停和买卖方向标记。输出是股票-日期级 `eligible` 矩阵。

### 一次典型流程

目标组合中有一只股票，但执行日它处于停牌。股票仍可保留在持仓中，但不能按新目标随意卖出或买入，账本记录限制。

### 结果如何理解

股票池是研究范围，可交易性是执行条件，两者都必须进入回测解释。

### 常见误区与限制

- 指数成员资格采用历史快照，不能用今天成分回看历史。
- ST 和上市天数会改变可买集合。
- 当前系统不模拟盘口排队和部分成交。

### 本节范围

不展开每个指数的成分快照来源。

## T6：策略适配器

### 先补基础知识

不同策略可以用不同方式产生目标：因子线性组合、因子排序、ML 排序或带状态的 provider。它们都需要输出统一的目标权重契约。

### 模块在项目中的位置

适配器位于 `trading/backtest/strategies` 和 `providers.py`。

### 它负责什么

它负责把策略输入转换成“每天每只股票的目标权重”。

### 它不负责什么

它不模拟成交、不维护真实现金，也不能绕过账本规则。

### 输入与输出

provider 输入行情、因子、eligible 和可选的上一遍持仓状态；输出同形目标权重矩阵。整行 NaN 表示不调仓，全 0 表示清仓。

### 一次典型流程

ML provider 读取某个模型的分数，在信号日选出前 30 只股票并输出等权目标。账本接着决定实际买多少股。

### 结果如何理解

provider 的输出是策略意图，不是成交记录。

### 常见误区与限制

- 部分 NaN、负权重、非 eligible 权重会被拒绝。
- 状态型 provider 可以读取上一次账本状态，但不能自行模拟成交。
- provider 版本变化会影响运行身份。

### 本节范围

不分析具体策略的选股公式。

## T7：目标权重与订单

### 先补基础知识

目标权重是“组合价值中想放多少比例”，订单是“买卖多少股”。中间还要考虑当前持仓、现金、价格和交易单位。

### 模块在项目中的位置

目标转换由 `signals.py`、`orders.py` 和 `allocation.py` 协作完成。

### 它负责什么

它负责将目标权重和当前组合状态转换为买卖方向、目标股数和订单意图。

### 它不负责什么

它不保证订单能成交，也不直接改变最终现金。

### 输入与输出

输入是目标权重、当前持仓、执行价格、现金和交易规则。输出是目标股数、订单数量和交易原因。

### 一次典型流程

当前持有 500 股，目标权重要求 800 股，系统形成买入 300 股的意图；如果最小单位或现金不允许，最终数量会被调整。

### 结果如何理解

订单是从旧状态走向目标状态的尝试，不一定是最后成交量。

### 常见误区与限制

- 目标比例不能直接乘收盘价得到真实订单。
- 订单方向和最终成交状态要分开记录。
- 现金缓冲会使实际股票权重低于目标。

### 本节范围

下一节说明分配和取整。

## T8：资金分配与最小交易单位

### 先补基础知识

A 股股票有申报单位和最小订单限制。资金也有限，多个买单需要在预算内分配。项目默认保留现金缓冲，避免把现金全部用完。

### 模块在项目中的位置

核心能力位于 `allocation.py` 和 `execution_state.py`。

### 它负责什么

它负责按执行日真实现金、持仓、价格、板块申报单位和现金缓冲分配目标股数。

### 它不负责什么

它不决定价格是否会继续变化，也不绕过成交额参与率限制。

### 输入与输出

输出包括 allocated shares、现金缩水、最小订单不足、取整余量和待补回状态。

### 一次典型流程

系统先计算卖出可释放的现金，再为买单按预算分配。主板通常按 100 股取整，科创板和北交所规则不同；预算不足的买单可能在后续交易日补回。

### 结果如何理解

最终持仓是整数股和有限现金约束下的可执行近似，不会精确等于目标权重。

### 常见误区与限制

- 高价股可能因为最小申报量无法买到目标比例。
- 现金缓冲本身会造成系统性权重偏差。
- 取整残差与真正被现金限制的缺口是不同事件。

### 本节范围

不展开固定点迭代的数学细节。

## T9：换手、单股上限与风险约束

### 先补基础知识

换手限制调节调仓幅度，单股上限限制集中度，行业上限限制组合在某个行业的过度暴露。

### 模块在项目中的位置

风险规则位于 `risk.py`，目标权重和分配由 `allocation.py` 继续处理。

### 它负责什么

它负责在目标组合进入分配前施加集中度、行业和单边换手等研究约束。

### 它不负责什么

它不保证实际成交后仍完全满足目标，也不代替真实流动性检查。

### 输入与输出

输入是目标权重、上一组合、行业和风险配置。输出是被限制后的目标或风险诊断。

### 一次典型流程

如果某股票目标权重超过单股上限，系统先限制目标，再在分配阶段按真实现金和持仓重新计算订单。

### 结果如何理解

风险约束改变的是策略意图，执行约束改变的是实际成交；两层不能混为一谈。

### 常见误区与限制

- 行业风险门通过不等于股票能成交。
- 换手限制可能让原有超配持仓分多次回落。
- 风险参数变化会改变策略版本或运行快照。

### 本节范围

不展开风险约束的全部优先级。

## T10：订单拒绝、重试与现金补回

### 先补基础知识

现实中订单可能被停牌、涨跌停、交易单位、资金或成交额限制拦截。若简单丢弃，组合会永远偏离目标；项目会记录拒单并在后续交易日重试部分订单。

### 模块在项目中的位置

相关状态由 `orders.py`、`allocation.py`、`execution_state.py` 和账本共同维护。

### 它负责什么

它负责记录不能成交的目标、保留必要的待重试状态，并在后续条件满足时继续尝试。

### 它不负责什么

它不假设被拒订单一定会在下一天成交，也不把未成交数量伪装成成交。

### 输入与输出

输出包括 rejection、retry_attempts、pending_at_end、cash_pending 和实际补单事件。

### 一次典型流程

股票因跌停无法卖出，持仓继续保留；之后每天重试，直到成交或区间结束。若买单因现金不足缩水，后续现金恢复后可以补回。

### 结果如何理解

拒单和重试是组合路径的一部分，会影响风险、换手和最终收益。

### 常见误区与限制

- 目标偏差不一定是算法错误，可能是市场交易约束的真实结果。
- 区间末仍未成交的持仓需要单独看待。
- 重试改变目标格数和换手统计口径。

### 本节范围

不展开所有拒单代码和事件字段。

## T11：A 股 T+1

### 先补基础知识

T+1 表示股票通常买入后不能在当天卖出。现金和股票持仓的可卖数量因此有时间限制。

### 模块在项目中的位置

规则由 `t1.py`、`execution_state.py` 和账本执行流程处理。

### 它负责什么

它负责区分当日新买入股数和可卖股数，阻止不符合 T+1 的卖出。

### 它不负责什么

它不决定股票是否涨跌，也不替代停牌和涨跌停规则。

### 输入与输出

输入是前一日持仓、当日买入和卖出意图。输出是可卖数量、T+1 拒单和剩余持仓。

### 一次典型流程

周一买入 100 股，周一不能卖出这 100 股；周二才进入可卖库存。若策略同日产生卖出信号，账本必须保留限制记录。

### 结果如何理解

信号可以很快变化，但持仓不能无限快地改变。T+1 会影响短周期策略的真实换手和风险。

### 常见误区与限制

- 研究分位曲线通常没有 T+1。
- 同一天的买卖顺序会影响可用股数。
- 当前日频策略的严格 T+1 账本应使不合法卖出为 0。

### 本节范围

不展开交易所规则的历史例外。

## T12：停牌与涨跌停执行

### 先补基础知识

停牌是没有正常交易；涨停或跌停是价格达到限制，方向不同会产生不同的成交可能。持仓还需要估值，即使当天不能成交。

### 模块在项目中的位置

输入状态来自数据层，执行规则由 `risk.py`、`orders.py` 和 `ledger.py` 处理。

### 它负责什么

它负责在交易方向上应用可买、可卖和价格限制，并对停牌持仓使用合理估值。

### 它不负责什么

它不模拟盘口队列、部分成交和撮合深度。

### 输入与输出

输出包括 no_price、rejection、实际成交和停牌估值状态。

### 一次典型流程

停牌股没有新的可成交价，持仓沿用上一有效收盘价估值；涨停股可能不能买入，跌停股可能不能卖出，状态和结果分别记录。

### 结果如何理解

回测收益可能包含“持有但无法调整”的组合状态，这与理想化每日按目标重平衡不同。

### 常见误区与限制

- 停牌估值不等于可以按该价格成交。
- 涨停价不等于买单一定成交。
- 退市处理是特殊风险边界，需单独看核销记录。

### 本节范围

不覆盖集合竞价和盘口仿真。

## T13：费用、滑点与冲击

### 先补基础知识

交易费用会降低收益。滑点是实际成交价偏离参考价，冲击是大订单对成交价的影响。它们可能很小，但高换手策略会反复累积。

### 模块在项目中的位置

费用定义在 `costs.py`，成交价和账本在 `ledger.py`、`orders.py`。

### 它负责什么

它负责计算佣金、最低佣金、印花税、过户费、滑点、冲击和递延红利税。

### 它不负责什么

它不从统计指标推断真实市场冲击，也不保证费率模型覆盖所有券商细节。

### 输入与输出

输出包括费用分项、成交金额、成本 bps、滑点和冲击归因。

### 一次典型流程

订单按原始开盘价加滑点成交，费用从成交事件中计算；滑点和冲击已经进入成交价，不能再重复从现金扣一次。

### 结果如何理解

净收益比毛收益更接近实际研究问题，但仍受成本假设影响。

### 常见误区与限制

- 年化收益好看但换手很高时，成本敏感度可能很大。
- 历史税费政策可能变化。
- 交易成本模型不是现实盘口的完整替代。

### 本节范围

不逐项列出费率表。

## T14：公司行动

### 先补基础知识

分红、送转、配股会改变现金、股数或持仓成本。如果不记账，组合净值会产生不真实的跳变。

### 模块在项目中的位置

公司行动数据来自 `ref.corporate_action`，账本处理位于 `corporate_action_ledger` 相关逻辑。

### 它负责什么

它负责在原始价格执行中调整股数、应收分红、配股认购和红利税批次。

### 它不负责什么

它不猜测没有可靠结构化映射的并购换股和复杂重组。

### 输入与输出

输出包括公司行动事件、零股现金、应收分红、配股、未认购股数和税务记录。

### 一次典型流程

除权日先处理送转和零股，现金分红在到账日进入现金，卖出时按 FIFO 批次结算红利税，配股在现金允许时认购。

### 结果如何理解

公司行动把“价格变化”转换为真实持仓和现金变化，是原始价回测不可缺少的一层。

### 常见误区与限制

- 后复权价格已经包含部分公司行动效果，不能再直接拿它和账本现金混用。
- 并购换股和北交所转板仍有已知未建模边界。
- 公司行动数据来源冲突时以项目规定优先级处理。

### 本节范围

不逐事件解释 Tushare 和 gbbq 的源数据差异。

## T15：账本与组合状态

### 先补基础知识

账本记录每天发生了什么。组合价值通常是：

```text
现金 + 应收分红 + 持股数量 × 估值价格
```

### 模块在项目中的位置

核心实现是 `LedgerPortfolio`、`ledger.py` 和 `execution_state.py`。

### 它负责什么

它负责把订单、成交、公司行动、费用和估值按日期顺序记入现金、持仓和净值。

### 它不负责什么

它不重新生成策略信号，也不替模型判断是否有效。

### 输入与输出

输出包括现金、持仓、平均成本、FIFO 批次、成交、每日净值和状态统计。

### 一次典型流程

每日先支付到期分红，再处理除权和配股，再按先卖后买执行订单，结算税费，最后按收盘价估值并生成日结果。

### 结果如何理解

账本是回测中最接近“实际组合会计”的部分，必须按顺序理解。

### 常见误区与限制

- 日结果不是简单把目标权重乘收益。
- 停牌股估值和成交是两个概念。
- 账本错误会同时污染净值、成本和归因。

### 本节范围

不解释内部状态对象的每个字段。

## T16：执行引擎与分块运行

### 先补基础知识

全 A 长历史数据很大，不能总是一次放入内存。分块运行会把历史划成资源块，但必须保留跨块的持仓、现金和 provider 状态。

### 模块在项目中的位置

分块位于 `chunked.py` 和 `pipeline.py`，执行引擎位于 `engine.py`。

### 它负责什么

它负责规划资源块、预热历史、连续传递状态，并让分块结果与整段运行保持同一因果顺序。

### 它不负责什么

它不把不同块当作独立回测，也不允许块边界重置持仓。

### 输入与输出

输出包括资源计划、块级事件、跨块状态和最终统一结果。

### 一次典型流程

系统按面板格数估计分块，块开始读取必要预热行，块结束保存组合和 provider 状态，下一个块继续执行。

### 结果如何理解

分块是资源管理方式，不应改变策略的时间因果关系。

### 常见误区与限制

- 直接 `load_market_data()` 超过上限会失败，不会自动分块。
- 分块边界的预热行不能被重复计入结果。
- 取消通常只在安全边界生效，不能中断正在执行的账本事件。

### 本节范围

不展开块规划算法。

## T17：风险与覆盖检查

### 先补基础知识

回测不仅要算收益，还要知道输入是否覆盖、风险是否超限、组合是否存在无法解释的偏差。

### 模块在项目中的位置

检查分布在 `coverage.py`、`risk.py`、`snapshot.py` 和 pipeline 预检阶段。

### 它负责什么

它负责发现数据缺口、面板错位、风险超限、现金异常和状态不一致。

### 它不负责什么

它不替研究者证明策略的统计显著性。

### 输入与输出

输出包括 coverage 摘要、风险诊断、错误码和拒绝原因。

### 一次典型流程

运行前检查日期、股票数、面板规模和策略配置；运行中检查现金、持仓、订单和状态反馈；运行后检查结果表和指标是否闭合。

### 结果如何理解

通过覆盖检查只能说明“数据和执行链路没有明显违反契约”。

### 常见误区与限制

- 没有错误不代表市场模拟完整。
- 资源上限是系统保护，不是策略质量门槛。
- 风险诊断应和实际持仓结果一起看。

### 本节范围

不列出全部错误码，工程文档会集中说明。

## T18：绩效指标

### 先补基础知识

净值是组合价值相对起点的变化。最大回撤描述从历史高点跌到之后低点的最深幅度。Sharpe 试图比较收益和波动，但依赖年化和独立性假设。

### 模块在项目中的位置

指标计算位于 `trading/backtest/metrics.py`。

### 它负责什么

它负责从已落库日结果重算收益、波动、回撤、Sharpe、Sortino、Calmar、换手和成本指标。

### 它不负责什么

它不修改账本结果，也不把缺失基准数据强行当成零。

### 输入与输出

有基准时还会输出 Beta、Alpha、跟踪误差、信息比率和超额；无有效基准时跳过这些字段但保留组合指标。

### 一次典型流程

系统从日结果读取组合净值和收益，按实际交易日数年化，再结合成本和可选基准生成指标摘要。

### 结果如何理解

指标描述的是这次模拟路径，不是策略未来的分布保证。

### 常见误区与限制

- Sharpe 高可能来自短样本或特殊市场阶段。
- 最大回撤不能说明恢复时间和流动性风险。
- 基准缺失时不能把基准相关指标解释为 0。

### 本节范围

不展开每个指标公式的统计推导。

## T19：归因与基准

### 先补基础知识

归因是解释收益来自哪里：买卖、费用、行业、现金、持仓或基准差异。基准是用来比较组合是否跑赢一个参考市场。

### 模块在项目中的位置

归因位于 `attribution.py`，行业暴露和基准字段由 pipeline 与 store 保存。

### 它负责什么

它负责拆分成交成本、行业暴露、现金比例、集中度和相对基准的表现。

### 它不负责什么

它不证明某个行业暴露是因果来源，也不替模型做风格中性化。

### 输入与输出

输出包括单边/双边换手、费用 bps、行业平均/最大/期末权重、现金和 HHI。

### 一次典型流程

系统按实际持仓和收盘价计算行业市值，而不是直接使用目标权重；现金和未分类股票也进入行业报告。

### 结果如何理解

归因帮助解释“收益和风险是怎么来的”，但不能把相关暴露直接说成原因。

### 常见误区与限制

- 行业报告使用实际持仓，和目标组合可能不同。
- 没有基准时，组合指标仍可用，但超额类指标不可用。
- HHI 高表示集中，不等于一定亏损。

### 本节范围

不展开报告页面的字段映射。

## T20：结果存储与读取

### 先补基础知识

回测结果不仅是一条净值曲线，还包括运行状态、输入快照、订单、持仓和拒单。持久化让结果可以复查和由 Web 页面读取。

### 模块在项目中的位置

存储由 `store.py`、`pipeline.py` 和 `snapshot.py` 负责。

### 它负责什么

它负责在事务中保存策略、运行、快照和多张结果表，并保证成功或失败状态清楚。

### 它不负责什么

它不自动修复半成品结果，也没有运行中删除的回收站语义。

### 输入与输出

结果表包括 `daily`、`position`、`order`、`rejection`、`target_weight`、`holding`、`allocation`、`liquidation`、`corporate_action` 和 `industry_exposure`。

### 一次典型流程

流水线先创建 running 记录，再执行账本，最后在一个事务中写结果表、metadata、snapshot 和 success。失败时回滚写入并标记 failed。

### 结果如何理解

落库状态是运行生命周期的一部分；只看到某张结果表存在不能代表运行完整成功。

### 常见误区与限制

- 直接 `run_backtest()` 只返回内存结果，不写数据库。
- 删除已结束运行会清理结果，没有回收站。
- 旧运行的字段兼容由读取层处理，不能随意改 schema。

### 本节范围

不列出每张结果表的全部字段。

## T21：CLI、API 与页面集成

### 先补基础知识

命令行适合批量和复现，API 适合页面交互。二者最终都应调用同一套策略、账本和存储能力。

### 模块在项目中的位置

CLI 入口是 `backtest/__main__.py`，Web 适配是 `apps/monitor/backend/backtest_service.py`。

### 它负责什么

它负责把创建策略、启动运行、查看状态、读取指标和对比结果暴露给用户。

### 它不负责什么

它不在 Web 层重写执行规则，也不把 SSE 事件当作新的账本逻辑。

### 输入与输出

输入是策略、区间、资金和基准参数；输出是同步结果或 `meta/load/.../done` 流式事件。

### 一次典型流程

页面创建策略并提交回测，后端先预检和预约容量，再启动后台任务。任务完成后页面通过运行 ID 读取日结果、指标和归因。

### 结果如何理解

API 是访问回测的入口，不改变回测本身的金融口径。

### 常见误区与限制

- 服务容量耗尽是调度问题，不是策略失败。
- API 返回成功只说明请求完成，仍需查看 run 状态和指标。
- 单 worker 是当前调度和共享锁正确工作的前提。

### 本节范围

具体页面交互放到监测应用文档。

## T22：端到端回测场景与限制

### 先补基础知识

一条完整回测链路需要同时经过数据、信号、目标、执行、账本和结果查询。任何单模块正确，都不能保证联动正确。

### 模块在项目中的位置

入口是 `backtest.pipeline.run/iter_run`，下游是 `BacktestStore` 和监测站。

### 它负责什么

它负责把一次策略运行从输入快照推进到最终绩效和归因。

### 它不负责什么

它不模拟所有市场微观结构，也不保证模型和因子的样本外价值。

### 输入与输出

输入是版本化策略、市场数据、因子或模型预测、资金和运行区间。输出是可查询的完整回测运行。

### 一次典型流程

以 ML 排序策略为例：读取冻结预测，生成周频目标，下一交易日执行，处理现金、T+1、停牌、费用和公司行动，保存日结果，再由页面读取指标。

### 结果如何理解

只有把模型分数、目标组合和账本结果串起来，才能解释“模型好不好”和“策略能否执行”之间的差异。

### 常见误区与限制

- 不模拟盘口深度、集合竞价队列、部分成交、融资融券和并购换股。
- 退市核销、公司行动和数据覆盖仍有明确边界。
- 回测结果不能替代新的未来窗口验证。

### 本节范围

不展开具体策略的参数优化。
