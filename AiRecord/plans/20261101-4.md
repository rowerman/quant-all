# 20261101-4 计划：让 V2 已批准候选接入正式发布链

- 日期：2026-11-01
- 版本：V139
- 类型：feat
- 进度任务：P0-03

## 目标

让 V2 已批准候选复用现有 `MiningPublicationService`，完成整批构建、全量校验、原子
发布、失败回滚和重试恢复。V2 候选、审批和研究证据继续以 `mining_v2` 为唯一事实来源，
不向 V1 运行、候选或审批表复制记录。

## 实现

### P0-03-A 来源适配

- 保持 `MiningPublicationService(store=...)` 入口，允许注入 `MiningV2Store`。
- V2 发布读取批准的候选和审批证据，并把冻结搜索上下文转换为仅用于构建的 V1
  上下文。
- 发布页输入的 `expected_context_hash` 仍绑定 V2 原始上下文。

### P0-03-B V2 发布状态

- 在 `MiningV2Store` 增加发布仓储能力，使用现有 `mining.publication_batch` 和
  `mining.publication` 保存正式发布事实。
- 在同一事务中完成候选 `approved/build_failed -> building` 和
  `building -> published/build_failed`、批次写入、V2 事件及链式轨迹。

### P0-03-C 整批约束

- 批次必须精确包含当前运行全部 `approved` 和 `build_failed` 候选。
- 漏选、混入其他状态、候选或审批证据变化均拒绝。
- 失败后保留 `build_failed`，按新的 attempt 整批重试。

### P0-03-D 并发与恢复

- V1、V2 共用单活动发布批次约束，避免同时切换同一正式因子目录。
- 启动恢复只处理对应来源的未完成批次。
- 未写 committed 日志的批次回滚并把候选置为 `build_failed`；已提交批次完成收尾。

### P0-03-E 来源审计

- `PublicationBatch` 增加默认值 `v1` 的 `source_kind`，旧发布记录通过 schema
  迁移继续可读。
- V2 批次和逐候选发布记录标记为 `v2_search`。
- 正式因子定义清单保留运行、候选、审批、上下文、轨迹和评分卡来源摘要。

### P0-03-F 提交前复核

- 正式提交前重新核对候选、上下文和审批证据。
- 复核失败时执行现有回滚路径，旧正式因子保持不变。

## 公共接口

- `MiningPublicationService` 的现有调用兼容，新增对 `MiningV2Store` 的来源适配。
- `PublicationBatch.source_kind` 是新增可选字段，默认 `v1`。
- 发布错误继续使用 `MINING-109`、`MINING-121`、`MINING-122`、`MINING-123`。
- 不新增 V2 专用发布器或正式因子目录。

## 测试

1. V2 单候选和多候选整批发布状态迁移。
2. 部分选择、混合批准与失败候选重试、证据变化和并发启动。
3. 跨 schema 启动失败回滚。
4. 构建、提交失败及进程中断恢复不改变旧正式因子。
5. V1 与 V2 未完成批次隔离，V1 原有发布、桥接和审批测试保持通过。
6. 定向回归、`py_compile` 和 `git diff --check` 通过。
