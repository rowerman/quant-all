# 20261101-5 计划：补齐 V2 审批与发布 Web 闭环

- 日期：2026-11-01
- 版本：V140
- 类型：feat
- 进度任务：P0-04

## 目标

在现有监测站路由和页面组件上补齐 V2 搜索候选的详情、人工审批、整批正式发布、
失败重试、状态展示和中断恢复入口。V1 页面与接口行为保持不变，V2 仍以
`mining_v2` 为运行、候选和审批的唯一事实来源，正式发布继续复用
`MiningPublicationService`。

## 实现

### P0-04-A 统一后端分流

- `MiningWebService` 对 `searchrun_` 的候选详情、审批和发布批次调用转发给
  `MiningSearchWebService`。
- V2 Web 服务持有基于 `MiningV2Store` 的发布服务，初始化、关闭和未完成批次恢复
  与 V1 来源隔离。
- 保持现有 HTTP 路径、请求字段和错误码，不建立第二套 V2 Web 契约。

### P0-04-B 候选详情

- 返回 V2 候选定义、五阶段评估证据、评分卡、审批资格、阻塞原因、审批记录、
  发布资格和最近发布批次。
- 使用冻结搜索上下文派生发布快照上下文，在页面展示审批时重新核对行情、目录和
  正式因子快照。
- 只返回审核所需的安全字段，不返回 Prompt、密钥、生产路径或无关运行数据。

### P0-04-C 审批与发布

- V2 审批沿用 `decision/reviewer/note/candidate_content_hash/evidence_hash`。
- 服务端重新读取当前审批资格并比较两个页面哈希，再调用
  `record_search_approval()`；保持相同决定幂等和相反决定冲突。
- V2 发布沿用 `candidate_ids/expected_context_hash`，整批包含全部
  `approved/build_failed` 候选，由现有发布服务完成构建、校验、提交和回滚。
- 活动批次期间拒绝重复启动；失败批次和 `build_failed` 候选可由页面重试。

### P0-04-D 页面

- V2 运行页候选行增加详情链接，并展示审批和发布后的候选状态。
- 候选页按 V2 的 `technical/development/selection/full/holdout` 阶段展示证据。
- 复用现有审批、发布、错误提示和后台刷新交互；刷新页面后从服务端恢复状态。
- 保持桌面与 390px 移动端可用。

### P0-04-E 验收与记录

- 增加 V2 Web API 联合测试，覆盖详情、批准、拒绝、哈希冲突、快照失效、
  整批发布、失败重试、并发批次和恢复。
- 增加确定性 V2 浏览器夹具和验收脚本，不调用真实 Worker 或正式数据。
- 更新 `FACTOR_MINING_PROGRESS.md`、挖掘 Web/API 文档、`AiRecord/version.md`、
  `progress/V140.md`、`changes/20261101-5.md` 和 `diffs/20261101-5.md`。

## 公共接口

- 路径不变：候选详情、审批和发布批次继续使用现有 `/api/mining/runs/...`。
- 审批字段和发布字段保持不变。
- V2 候选详情的公开字段与 V1 共用基础结构，并增加分阶段证据、评分卡和
  `blocking_reasons`；V1 返回结构保持兼容。

## 测试

2. V2 候选详情、筛选资格、哈希冲突、幂等审批和快照失效。
3. V2 全部批准候选整批发布、部分选择拒绝、失败重试、活动批次与恢复。
4. V2 页面批准、拒绝、发布、重试、刷新恢复和移动端浏览器验收。
5. 定向测试、`py_compile` 和 `git diff --check`。
